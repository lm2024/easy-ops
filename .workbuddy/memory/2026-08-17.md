# 2026-08-17

## 生产事故：ops.mv.db 膨胀 10GB 磁盘满（H2 救援）

- 现象：生产 `ops.mv.db` 占 ~10GB，磁盘占满，server 无法启动；环境无法下载大文件。
- 根因：H2 MVStore 日志结构存储，**DELETE 只标记空闲页、文件不自动缩小**；`nginx_minute_stat`(分钟×IP×URI×方法预聚合)/`nginx_ua_stat`/`nginx_referer_stat`/`nginx_request_sample`/`monitor_snapshot`(心跳快照) + 日志类表无限累积。
- 解法（全程服务器本地，无需下载文件）：停 server → 按保留期 DELETE 历史数据 → `SHUTDOWN COMPACT` 原地压缩回收空闲页。验证：5 万行 6.6M → 删 4.5 万行 → 304K。
- 交付脚本：`scripts/rescue-h2.sh`（本仓库根下）。参数：`<data目录> [server.jar路径] [--yes] [--dry-run]`，环境变量 `KEEP_DAYS=7`(统计/监控类) `LOG_KEEP_DAYS=30`(日志类)。脚本自动从 server fat jar 提取 h2 驱动、磁盘紧张时先清日志、自动跳过无时间字段的表、不碰系统配置/元数据表。cron 建议每周跑一次。
- 坑：① H2 URL **不能带 `.mv.db` 后缀**（会建 `xxx.mv.db.mv.db` 空库）；② `SHUTDOWN COMPACT` 末尾报 "already closed" 是 Shell 收尾重复关闭的无害提示，压缩实际已生效（文件明显缩小即证）；③ bash 变量后紧跟全角字符（如 `$tbl（`）在非 UTF-8 locale 下会当变量名解析报 unbound，须用 `${tbl}`。
- H2 连接：`jdbc:h2:file:<dir>/ops;MODE=MySQL`，sa 空密码，版本 2.2.224。

## 追加：审查定时清理（DataCleanupScheduler）发现 3 个漏洞并修复
- ① `table-retain-days` 是死配置：YAML map 展开成扁平 key，`@Value` 读不到，代码从未读取（grep 零引用），按表保留天数从未生效，全部统一走 retain-days:3。修复：新建 `config/CleanupProperties.java`（@ConfigurationProperties 绑定）+ scheduler 按表取覆盖值。
- ② `script_distribute_record` 漏清理：mapper 只有增查改，无 deleteBefore，scheduler 未注册 → 无限累积。修复：mapper 加 deleteBefore + scheduler 补任务 + yml 加配置。
- ③ **根本原因**：定时清理只 DELETE 不 COMPACT。H2 MVStore 删除只标记空闲页，ops.mv.db 物理文件只增不减，哪怕天天删行，文件照样涨到爆盘。唯一释放手段：停机 `SHUTDOWN COMPACT`（rescue-h2.sh 已有）或迁 MySQL。必须配每周停机压缩 cron。
- 已确认无问题项：@EnableScheduling 已开、scheduler_lock.expire_at 字段匹配、monitor_snapshot 按 collect_time 删正确、notification_record 创建时有 expire_time 兜底赋值（不会 NULL 漏删）、nginx 子查询 LIMIT 分批删除在 H2 2.2 正常（自动转 FETCH FIRST）、project_health_probe 每项目一行（唯一索引）非流水、node_config_snapshot/node_script_snapshot 是 upsert 型不累积。
- 改动文件（已编译通过）：CleanupProperties.java(新)、ScriptDistributeRecordMapper.java/.xml、DataCleanupScheduler.java、application.yml。server 需重新构建部署。

## 追加：防爆盘三层防线 + 交付 prevent-disk-full.sh
- 方案：① 每周停机压缩（rescue-h2.sh）② 磁盘水位 check 告警 ③ 源头控写入+迁 MySQL。
- 交付 `scripts/prevent-disk-full.sh`：双模式 `check`（只读告警，阈值默认75%，每小时 cron）/ `compact`（磁盘超阈值才停机压缩，默认85%，每周 cron；未超跳过避免无谓停机）；支持钉钉/企微 webhook 钩子。已本地验证。
- 复用教训：bash 变量后紧跟全角标点（`$DATA_DIR。`）会 unbound，必须 `${DATA_DIR}`。

## 追加：验证 H2 关闭时自动压缩 + 实现程序内自动重启回收
- 实验（H2 2.2.224 实测）：插入 20 万行=28MB → 保持连接删 90% → **181MB（DELETE 大事务注水，反涨 6 倍）** → 保持打开 30s 不缩 → **关闭连接自动压缩到 2.8MB**（缩 64 倍）。
- 结论：H2 MVStore 只在【数据库关闭】时自动压缩；运行中删除不回收反而注水 → 这就是"天天清理还爆盘"的精确机制。
- 实现：DataCleanupScheduler 加 `easyops.data.cleanup.auto-restart`(默认false) + `restart-threshold-pct`(默认80)，清理后磁盘超阈值 → 延迟 3s System.exit(0) 优雅退出 → H2 关闭自动压缩 → 由外部守护拉起。⚠️前提：必须 systemd/docker --restart/守护脚本拉起，否则服务停。已编译通过。
- 三选一：程序自动重启（推荐，需守护）/ 外部 rescue 脚本停机压缩 / 迁 MySQL（终局）。

## 追加：修正磁盘水位判断为「db 实际所在盘」
- 用户指出 auto-restart 的磁盘判断不能是 cwd。已改为：从 `spring.datasource.url`（jdbc:h2:file:<路径>/ops）解析 db 真实目录 → `resolveDbDir()` → Files.getFileStore(dbDir) 判断该盘；拿不到配置时从连接 getMetaData().getURL() 兜底，最后才回退 cwd。日志打印"数据库所在盘: <dir>"便于核对。已编译通过。

## 追加：改为"启动时瘦身"（用户纠正设计，更合理）
- 用户指出：等磁盘满才压缩不合理（满了可能起不来=死循环），应**每次启动前先压缩**。
- 已改 `backend/server/start.sh`：启动 java 前先检查 `$SERVER_DATA/ops.mv.db`，超 `COMPACT_THRESHOLD_MB`(默认256，设0强制) 则从 fat jar 提取 h2 驱动执行 `SHUTDOWN COMPACT`（残留 .lock.db 先删；压缩失败不阻断启动）。已验证：6.6M→2.5M，压缩先于启动执行。
- 新推荐流程：每周定时重启 server（stop+start，start 自带瘦身）即可，磁盘永远健康；prevent-disk-full.sh / auto-restart 降级为可选项。
