## 监控中心 PID 显示 bug 排查与修复

### 问题现象（用户反馈）
- 监控中心「应用监控」sheet：详情页打开后**经常**显示「进程未运行或 PID 未知」；列表无 PID 列。
- 「Agent 状态」sheet：显示的是 **Agent 自身 PID**（agentPid，来自心跳 `X-Agent-PID`），一直正常。
- 用户怀疑：详情取错了，取成了 Agent 状态 sheet 的 pid。实际不是——详情用的是 `processPid`（应用 PID）。

### 根因（已用 H2 数据证实）
`monitor_snapshot` 表 `PROCESS_PID` 在每行都为 null 且 `PROCESS_STATUS/HEALTH_STATUS` 在 RUNNING/UP 与 STOPPED/DOWN 间抖动。
- 心跳（Agent→Server，`NodeController`/`HeartbeatDaemon`）扫描真实文件系统 `/app/data/apps/`，能拿到真实应用 pid 并写入 `processPid`。
- 后台采集器（`MonitorCollectorService.collectOne`，由定时/手动刷新触发）用**项目配置的 deployDir/jarName** 调 Agent `/process/status`；当该次探测超时/未匹配时，会写入一条**新快照且 processPid=null**，**覆盖**心跳的好数据。`findLatestByNodeIds` 取最新行 → 详情读到 null → 间歇「PID 未知」。

### 修复内容
1. `MonitorCollectorService.collectOne`：改为「合并」而非「覆盖」——以最近快照为基线，仅在 Agent 真正可达且进程确停(persist 模式)时清空 PID；Agent 不可达或瞬时探测失败时**沿用基线 PID**，绝不误清空。
2. 新增 `collectOne(project, node, boolean persist)`：`persist=false` 为详情实时刷新（不落库、不告警），即使瞬时探测失败也保留基线 PID。
3. `AppMonitorController`：`buildNodeInfo` 增加返回 `agentPid`（节点自身 PID）；新增 `/monitor/app/node/refresh` 实时采集单个节点用于详情页。
4. 前端 `AppMonitorView.vue`：应用监控列表新增「进程PID」「AgentPID」两列。
5. 前端 `InstanceDetailDrawer.vue`：详情标题与基础指标同时展示「进程PID」与「Agent PID」；打开详情时调用 `refreshAppNodeDetail` 实时拉取真实 PID（失败则保留快照数据）。
6. 前端 `types/index.ts`、`api/monitorApp.ts`：补充 `agentPid` 字段与 `refreshAppNodeDetail`。

## 11:12 深入排查 Agent 升级的部署目录要求（用户问按钮升级对目录是否有要求、jar 落哪）
- 完整链路：前端「Agent 升级」按钮 → Server `POST /api/agent-upgrade/upload`（jar 存到 **Server 自己**的 `{server.path}/agent-packages/{ver}.jar`，与 Agent 机无关）→ Server `POST /api/agent-upgrade/upgrade` 逐节点 multipart POST 到 Agent `POST /system/upgrade` → Agent 端 `AgentUpgradeService.upgrade()`。
- 关键代码：`AgentUpgradeService` 注入 `@Value("${agent.jar-path:/app/agent.jar}") jarPath`；`upgrade()` 里 `targetJar = new File(jarPath)`（L146）。升级**只替换并重新启动 `agent.jar-path` 这个文件本身**；而 `agent.data-path`（默认 `/app/data`）仅用于 staging/备份/version文件/日志（工作台），不是运行 jar 落点。
- 重启逻辑：Docker 模式 `System.exit(0)` 交给容器 restart 拉起（entrypoint 固定 `java -Dagent.jar-path=/app/data/agent.jar -jar /app/data/agent.jar`）；裸机 shell 模式生成 restart-agent.sh，`setsid nohup java -jar "$AGENT_JAR"` 且 `AGENT_JAR=targetJar=agent.jar-path`，并 export `AGENT_JAR_PATH/AGENT_DATA_PATH/AGENT_UPGRADE` 等。支持配置 `agent.restart-script` 走用户自己的 start.sh。
- 结论给用户的重点：升级对 `apps/agent` 这类"应用部署目录"**无任何要求**；真正要求是 **`agent.jar-path` 必须指向 agent 实际运行的 jar**。生产若从 `apps/agent/xxx.jar` 启动却没设 `AGENT_JAR_PATH`，会默认落到 `/app/agent.jar` → 升级替换/重启的是错的 jar，`apps/agent` 原 jar 不被替换。推荐：①设 `AGENT_JAR_PATH=绝对路径/apps/agent/easy-ops-agent.jar`；或②设 `agent.restart-script` 指向自有 start.sh（升级会注入环境变量）。

## 11:22 纠正用户"端口冲突导致升级失败"的判断（Agent 升级时序核查）
- 用户假设：`apps/agent` 已启动的进程无法升级，因为新 jar 落到 `/app/agent.jar`，拉起时端口冲突→升级失败。
- **实证推翻该假设**：升级重启时序不会端口冲突。`scheduleRestart` 中 `oldPid=currentPid()`(L187) 取到当前 apps/agent 进程的 PID；L214 先启动后台重启脚本（脚本进入 `kill -0 $OLD_PID` 轮询等待，L131-141，最多30s）；随后 L217-218 当前 Agent **自己 `System.exit(0)` 杀掉自己**（即 apps/agent 进程）；脚本确认旧 PID 退出后才 `setsid nohup java -jar /app/agent.jar` 拉起新版（L150-153）。端口先释放后占用，不撞。
- **真正的坑（比端口冲突更阴）**：①升级"成功"后跑的是 `/app/agent.jar` 而非 apps/agent 的 jar，磁盘上 apps/agent 原 jar 原封不动（只被杀未替换），下次用 apps/agent/start.sh 手动重启会**静默滚回旧版本**；②首次升级若 `/app/agent.jar` 之前不存在，L196 `if(targetJar.exists())` 导致**不备份**，新 jar 起不来时无备份可回滚→可能两头落空。
- 结论：端口冲突不是真实失败模式；真正要解决的是 `agent.jar-path` 指错导致版本来源错乱。修复同前：设 `AGENT_JAR_PATH=绝对路径/apps/agent/easy-ops-agent.jar`。

## 11:31 排查"生产改密码导致 Server 启动报错、开发不报错"（密码启动链路）
- 用户现象：生产改了 admin 密码后 Server 无法重启、启动报错；开发环境改密码从不报错。
- **核心结论（反直觉但代码佐证）**：单改"密码内容"本身**不可能**让 Server 启动崩溃。
  - 启动期碰密码的代码仅 `DataInitializer.initAdminUser()`（`@EventListener(ApplicationReadyEvent)`）：读 `adminConfig.getDefaultPassword()`，空则 `warn` 跳过；非空则 `BCrypt.hashpw(defaultPwd, gensalt(10))` 写库。**无任何密码复杂度/长度/字符校验，BCrypt 吃任意字符串不抛异常**。
  - `PasswordValidator` 仅在 `SystemController.createUser/updateUser`（运行时 API）调用，不参与启动，故不会造成启动崩溃。
- **启动期唯一会抛异常的配置校验** = `SecurityConfig.validateSecurityConfig()`（`@Bean CommandLineRunner`，`@Order(0)`）：强制校验 `jwt.secret`——为空抛 `IllegalStateException("SECURITY VIOLATION: jwt.secret is not configured")`；长度<32 抛 `IllegalArgumentException("JWT_SECRET must be at least 32 characters")`。**它查的是 jwt.secret，不是密码**。
- **为什么生产有、开发没有（两处环境差异）**：
  1. **密码不是 env 可覆盖项**：`server/start.sh` L48-55 只传 `-Dserver.port/jwt.secret/agent.data-path/...` 等6个参数，**没有 `-Dapp.admin.default-password`**；`server/easyops.env` 也没设它。故生产密码**只能来自 `application.yml` L65 硬编码**。改生产密码必须编辑 YAML。若新密码含 YAML 特殊字符（如 `#` 注释、`#` 之前的 `#`、`: `、未加引号的 `[` 等）且未加引号 → YAML 解析异常 → 启动崩溃。这正是"开发用 Admin111!/Admin123! 没事、生产一改就炸"的典型（dev 默认值恰巧无特殊字符）。
  2. **JWT_SECRET 在 prod 靠 env**：`application.yml` L58 `${JWT_SECRET:超长默认}`；dev 用默认永不过；prod 靠 `easyops.env` L11 的 `JWT_SECRET`。用户改密码时若顺手动了 JWT_SECRET（删/改短/值含破坏 `-Djwt.secret="..."` 传参的双引号等）→ 启动在 SecurityConfig 抛异常，极易被记成"改密码报错"。
- **诊断方法**：看 Server 启动日志异常——含 `yaml`/`while scanning`/`could not resolve placeholder` → 原因1(YAML 被密码特殊字符写坏)；含 `SECURITY VIOLATION`/`JWT_SECRET must be at least 32` → 原因2(JWT_SECRET)。
- **修复建议（待用户确认是否动手）**：①立刻止血：application.yml L65 密码加双引号 `"..."`；②根治：在 start.sh 加 `-Dapp.admin.default-password="$ADMIN_DEFAULT_PASSWORD"` 并在 easyops.env 加 `ADMIN_DEFAULT_PASSWORD=...`，使密码走 env、不碰 YAML，符合"YAML 不动"部署规范，消除原因1。

## 14:41 修复"前端应用部署被监控误报异常"的 bug
- 用户现象：部署前端应用 dist 到 3 个节点后，收到 `🔔【dist】auto-registered-xxx 异常` 通知（三个节点都报），以为部署失败。

## 16:28 修复"应用监控列表 PID 串项目 + 前端显示后端 PID/堆"的严重 bug
- 用户现象：应用监控 dashboard 中前端应用 `dist` 在 3 个节点上显示出 **真实 Java 进程 PID（8769/1207）和堆内存（164/1024MB）**。用户指出：前端项目根本没维护 PID，这是严重 bug；后端应用 PID 应按"项目中配置的应用名称"精准获取。
- **根因 1（dashboard 快照按节点维度，跨项目串用，最严重）**：`MonitorSnapshotMapper.xml` 的 `findLatestByNodeIds` SQL 是 `GROUP BY node_id`（不带 project_id）。dashboard 把结果按 `nodeId` 单键塞进 `snapMap`（AppMonitorController L114-122、L136 `snapMap.get(nodeId)`），**每个项目在同节点上都查到同一条"节点级最新快照"**——而那条快照属于最后在该节点采集的应用（恰好是某后端 Java 应用）。于是前端 `dist` 显示成了别人后端应用的 PID/堆。该 bug 对同节点多后端应用同样串 PID。
- **根因 2（前端参与进程监控）**：`MonitorCollectorService.collectOne` 对**所有项目类型**无条件执行 `/process/status → /process/metrics → /process/jvm`。前端项目 `dist` 用 `deployDir=/nginx, jarName=dist.jar` 去 Agent 查，Agent `ProcessStatusChecker` 用 `ps aux | grep '/nginx' | grep 'dist.jar'` 命中了同节点其它 JVM，返回 alive=true+某 PID，进而采集到堆内存。上一轮的 frontend 修复只覆盖健康状态，没拦住进程/PID/堆采集。
- **修复**：
  1. Mapper 新增 `findLatestByProjectNodeIds`（`GROUP BY project_id, node_id`，JOIN 带 project_id），专供 dashboard 按 (项目,节点) 维度取各自最新快照；原 `findLatestByNodeIds`（按节点）保留给 Agent 状态页（L472）不变。
  2. `AppMonitorController.dashboard` 改用新方法，并以 `projectId+"_"+nodeId` 复合键存取 `snapMap`。
  3. `MonitorCollectorService.collectOne`：方法顶部提前算 `isFrontendApp`；前端分支**跳过 `/process/status` 调用**，显式 `setProcessStatus("N/A")`、`setProcessPid(null)`，不采集堆内存；健康状态写入块增加 `if(isFrontendApp){ setHealthStatus("UP")... }` 前置分支。删掉原 L356 处重复的 `isFrontendApp` 声明。
  4. 前端 `AppMonitorView.vue`：应用PID 单元格 `processStatus==='N/A'` 时显示"静态资源"；内存单元格前端显示"堆: -"；`processLabel` 增加 `'N/A':'静态资源'` 映射。
- **验证**：`mvn compile -pl server -am -DskipTests` EXIT=0；前端 `vue-tsc --noEmit` EXIT=0。
- 生效方式：后端改完需重新 `mvn package -DskipTests` + **重启 Server**；前端刷新/重新 build。重启后下一轮采集覆盖旧串用快照，前端行显示"静态资源 / N/A"，后端行显示各自正确的进程 PID。
- **残留点（待用户决定）**：`NodeController.saveMonitorSnapshot`（心跳落库）仍取 `processes.get(0)` 写 `process_pid`、且 project_id 取该节点第一个关联项目——这会污染"节点首个项目"的快照；但 dashboard 现已按 (项目,节点) 查 collectOne 的正确快照，显示不受影响。若要彻底根治心跳路径，需让心跳按每个 project 的 deployDir+jarName 匹配进程。用户未要求，暂未改。
