## 修复：应用 PID 不实时（与 CPU 不同线路）+ 自动刷新饿死状态字段
用户发现监控中心「等很久应用 PID 不变、手动刷新才变」的诡异现象。根因两层：
1. **架构分层**：`/ws/monitor` 的 `monitor_update` 原只推主机级 CPU/内存/磁盘；`processPid/processStatus/healthStatus/heap` 等应用级状态走 60 秒一次的 HTTP 轮询(`getAppDashboard`→`mergeDashboard`)，不在 WS 上。
2. **更隐蔽的饿死 bug**：`scheduleNextRefresh` 里 `if (wsConnected && wsMsgCount>0) 跳过本轮 fetchDashboard` —— WS 越健康，状态字段的 HTTP 轮询越被彻底跳过，导致 PID/状态几乎只在手动刷新时更新。
3. 后端 `saveMonitorSnapshot` 原把 `computed` 设为「最后一个项目」的状态，同节点多项目时 WS 只带一个项目的状态会串到别的项目。
修复（后端+前端，均已编译/构建通过）：
- 后端 `NodeController.saveMonitorSnapshot` 返回 `Map<Long, Map<String,Object>>`(按 projectId 维度)，`broadcastMonitorUpdate` 把 `computed` 按 projectId 推到 WS；`saveOneSnapshot` 已算好 processPid/processStatus/healthStatus/heap 等。
- 前端 `AppMonitorView.vue`：`nodeIndexMap` entry 加 `projectId`；`updateMonitorData(nodeId, metrics, computed)` 按 `projectId` 精确 patch 应用级状态到对应行（PID/状态/健康/堆 与 CPU 同走一条 WS 线路）；`ws.onmessage` 传 `data.computed`；`mergeDashboard` 把状态字段也纳入 `collectTime` 保护（WS 实时值优先，HTTP 仅作权威兜底，避免轮询反咬）；`scheduleNextRefresh` 改为 WS 正常时**延长**而非**跳过** HTTP 轮询(≥30s 兜底)。
- `npx vite build` 重出 nginx/dist（新 AppMonitorView chunk `4yZuY6Jp`），server `mvn compile` 通过。
- 结论：现在 PID/状态随 WS 心跳(秒级)实时跳动，与 CPU 同线路；HTTP 每 60s 仅作列表级兜底。
