# 2026-07-28 工作日志

## 应用监控页面"加载慢"排查（续昨天）

用户反馈"应用监控 一直加载中 / 现在能显示了但加载特别慢 / 是不是改了架构"。今天彻底定位。

### 结论：慢与代码改动无关，根因是本地 HTTP 代理拦截 localhost

- **架构未改**：dashboard 仍是 PUSH 读库模型。所谓"self check 自动上报"点 = Agent 端 `HeartbeatDaemon.sendHeartbeat()`（`@Scheduled(fixedRateString="${agent.check-interval:30}000")`，每 30s）POST 到 Server `/nodes/heartbeat` → `NodeController.saveMonitorSnapshot` 落 `monitor_snapshot`；dashboard 读该表。
- **后台还有 PULL 采集**（预存代码，非我写）：`MonitorCollectorScheduler` 每 `collectIntervalSec`(默认60, MIN60) 调 `collectAllAsync()` → 对每(项目,节点)同步 HTTP 拉 Agent（`collectOne` 内含 3 次 HTTP）→ 写快照。它为展示补充"按项目正确的 PID/JVM"，心跳只写节点首个进程。
- **证明后端不慢**：循环跑 dashboard 那条 `findLatestByProjectNodeIds` 查询 75 秒（覆盖完整采集周期），`samples=147, min=0ms, max=12ms, avg=0ms, spikes(>200ms)=0`；Server 日志无 HikariPool/连接超时/慢查询；采集器 INSERT 全在同 1 秒完成（快）。
- **真凶 = 本地代理**：环境设 `HTTP_PROXY=https://127.0.0.1:7897`（Clash/V2Ray 类）。vite dev server 监听 `[::1]:3000`，`localhost` 解析到 `::1`，而代理绕过列表只含 IPv4 `127.*`，故浏览器/请求被强制走 7897 → 每个请求多等 ~2s 甚至失败（`http=000`）。
  - 实测：走代理访问 localhost:3000 → `http=000, ~2.2s`；加 `--noproxy '*'` 直连 → `http=200, 0.01s`；直连 8081(Server) → 0.009s。
  - 这也解释了"之前很快"（代理关着）、"一直加载中"（代理开着且失败→请求挂起）、"能显示但慢"（代理通但 +2s）。

### 给用户的修复建议（环境侧，非代码）
1. 开发时关闭系统/浏览器代理（127.0.0.1:7897），localhost 直连即瞬间恢复。
2. 或把 `localhost;127.0.0.1;[::1]` 加入代理绕过列表（当前 NO_PROXY 缺 `[::1]`）。
3. 或浏览器用 `http://127.0.0.1:3000` 访问（IPv4，在绕过列表内）——但 vite 默认只绑 `[::1]:3000`，需在 vite.config 设 `server.host: true` 才同时监听 IPv4。

### 验证用过的诊断手段（可复用）
- JDBC 直连 H2（`jdbc:h2:file:.../data/ops;MODE=MySQL;AUTO_SERVER=TRUE`，JDK8 + h2-2.2.224 jar，用 `javac`+`java` 直接跑，不要走 Git Bash 的 mvn 脚本）查 `monitor_snapshot` 行数/索引/耗时。
- `curl` 带 `--noproxy '*'` 对比走代理与否的 localhost 延迟，快速识别代理拦截。
- 读 `data/logs/server.log` 看采集 INSERT 时间窗与连接池告警。
